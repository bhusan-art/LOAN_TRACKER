# 03 — Data model

`ledger_entry` is the source of truth. `due` rows are immutable skeletons written
by the daily job; `allocation` rows are a regenerable cache the job rewrites
atomically. Neither is ever written by hand, and due status/paid/waived values
are engine outputs, not stored columns.

| Table | Key fields | Notes |
|---|---|---|
| party | id, name, phone, address, id_proof_ref, guarantor, notes, risk_tag, created_at | Anyone the owner lends to or borrows from; can be on both sides. DELETE blocked, UPDATE allowed |
| loan | id, party_id, direction (GIVEN/TAKEN), book (BUSINESS/PERSONAL), principal_paise, start_date, rate, rate_unit (PER_MONTH/PER_YEAR), interest_type (SIMPLE/COMPOUND/EMI), interest_cycle (MONTHLY/QUARTERLY/AT_MATURITY), due_day, grace_days, penalty_rule, tenure_months, maturity_date, collateral, purpose, status, created_at | The agreement. Rate changed only via RATE_CHANGE entries; status maintained by the daily job |
| ledger_entry | id, loan_id, entry_date, type, amount_paise, payment_mode (CASH/UPI/BANK), reference, note, new_rate, reverses_id, created_at | Types: DISBURSE, TOPUP, PAYMENT, WAIVER, PENALTY, RATE_CHANGE, CAPITALISE, REVERSAL. No PRINCIPAL_PREPAY (#13). Append-only; a REVERSAL row's `reverses_id` points at the original (UNIQUE) |
| allocation | id, ledger_entry_id, due_period_start (nullable), bucket (PENALTY/INTEREST/PRINCIPAL), amount_paise | How each payment was split. Regenerable cache, rebuilt atomically when the ledger changes; INTEREST buckets reference a due by (loan, period_start) |
| due | id, loan_id, period_start, period_end, due_date, interest_paise | One IMMUTABLE skeleton per cycle, generated by the daily job (unique (loan_id, period_start)). paid/waived/penalty/status are engine outputs, never stored |
| funding_link | id, taken_loan_id, given_loan_id, amount_paise, link_date | Which borrowed money funded which given loan. Many-to-many. Unlinked part of a GIVEN loan = own capital |
| reminder_log | id, loan_id, due_date, kind, channel, sent_on, sent_at | Prevents duplicate reminders; dedupe UNIQUE (loan_id, due_date, kind, channel, sent_on). Keyed by loan + due_date so projected dues (no row yet) can be reminded |

Implementation note: `due` and `allocation` are caches rebuilt from the ledger on every change (services.recompute_loan); app_user and job_run were added in Phase 3.
Optional later: audit_log (when second user exists), attachment (promissory notes, cheque photos).
Indexes: ledger_entry(loan_id, entry_date), due(due_date), loan(book, direction,
status), reminder_log(loan_id, due_date, sent_on).

## Business vs personal books
- `book` is required on every loan. Moving a loan between books = logged adjustment, never a silent edit.
- Entries, dues, allocations inherit the book of their loan (no book column on them).
- UI toggle: All (default, consolidated) / Business / Personal. Remembered per device, shown as a coloured badge.
- Cross-book funding: a funding_link may join a TAKEN loan in one book to a GIVEN loan in the other.
  Allowed, but flagged with a warning badge and listed in a "Cross-book funding" report.
- Reports per book: interest earned, interest paid, net interest income per financial year (Apr-Mar).
  Kept separate because business and personal interest are typically taxed differently (confirm with a CA).
- Notifications tagged [BIZ] / [PER]. One book's reminders can be muted, except payables overdue.
- Later: business-only expense ledger (agent fees, legal costs).
